# School demonstration: account-restricted deployment

Status (2026-11-16): **prepared locally, not deployed.** No cloud resource, account, billing
link or public endpoint has been created. Everything under "Verified" was verified in the
local Firebase emulators only. Nothing here has been tested in a cloud.

The demonstration is the real application, restricted to invited accounts, analysing one
approved public video from pose data that the pretrained models produced for it earlier.
It is not a product launch, not real inference on new uploads, and not Phase 9B.

## 1. What the demonstration does

Login → upload "Front Crawl Underwater" → Analyze → status → results → feedback → playback.

- Approved video: `Front_Crawl_Underwater.webm`, Wikimedia Commons, by "It is a wonderful
  world", CC BY-SA 4.0, 12,560,020 bytes,
  SHA-256 `ce32d556ba1399b9dd5000f9a079475ca33377a9280cf30619a566ff8e9523c3`
  (https://commons.wikimedia.org/wiki/File:Front_Crawl_Underwater.webm; "Original file").
  The match is on the bytes: a re-encoded or trimmed copy is a different video.
- Pipeline: upload to Storage → job queued on the video document → worker downloads the
  file, hashes it → saved RawPose for that hash (`demo_fixtures/pose/<sha256>.rawpose.npz` in
  the project's bucket, backend-only) → the usual checks against the video → cleanup,
  metrics, interpretation, feedback, exactly as in development. Nothing is hardcoded.
- Any other video fails with: "This video can't be analysed in the demonstration
  environment…" (not retryable). No other video's data is ever substituted, and a pose file
  stored under the wrong hash is still rejected by `validate_raw_pose`.
- The upload page and every result built on saved pose data say so (`DemoNotice.tsx`).
- YOLO11m and RTMW-x are pretrained models that AquaTrack did not train. They do not run
  in the demonstration and their weights are not deployed.

## 2. How access is restricted

| Layer | What enforces it |
| --- | --- |
| Backend | `AQUATRACK_ACCESS=restricted`: every route that takes a user refuses a uid not in `AQUATRACK_ALLOWED_UIDS` with 403 (`api/firebase.py`). Anything but `open` is treated as restricted. |
| Firestore, Storage | `firebase/restricted/*.rules`: the normal rules plus a required custom claim `aquatrack_demo`. Generated by `scripts/build_restricted_rules.py`; a test fails if they are stale. |
| Claim | Set by the backend at start on the listed accounts that exist, removed (and sessions revoked) from all others. Creates no account. |
| Web app | Sign-up page closed, login checks `/access`. Interface only; not relied on. |

Sign-up: the web app cannot create accounts in this mode, but Firebase's sign-up endpoint
is public for any project with email/password enabled. Turning it off is a console setting
(Authentication → Settings → User actions → "Enable create (sign-up)"); whether that
needs the Identity Platform upgrade was **not confirmed** — check it in the console. Either
way, an account created that way has no claim and is not listed: it can sign in to
Firebase and do nothing else (emulator-tested: backend 403, Firestore 403, Storage 403).
Accounts are listed by uid, not email, so nobody can get in by registering an invited
address first.

## 3. Where saved pose data may run

`config.fixture_problem()` and `demo.build_pose_source()`: in a real project the precomputed
source is built only when `AQUATRACK_ENV=staging`, `AQUATRACK_DEMO=1` and
`AQUATRACK_ACCESS=restricted` are all set. Otherwise the job runner is not created at all.
`AQUATRACK_DEMO=1` is refused in production. Local development is unchanged.

## 4. Recommended hosting

| Part | Service | Why |
| --- | --- | --- |
| Web app | Render web service (Node), `aquatrack-demo-web` | Runs `next start` as is; `/api/*` is forwarded to the API, so the browser has one origin and no CORS is needed. |
| API + worker | Render web service (Python), `aquatrack-demo-api` | One always-on process: FastAPI plus the embedded worker thread. CPU only; a 13 s clip analyses in a few seconds locally. |
| Auth, Firestore, Storage | The existing AquaTrack Firebase project if section 4a's checks pass; otherwise the smallest alternative agreed with the owner | Same services the code already uses. |

The queue is the Firestore video documents themselves (leases, heartbeats, recovery), so it
needs no extra infrastructure and a job survives a restart. `render.yaml` describes both
services; nothing applies it automatically.

Not chosen: Firebase App Hosting / Cloud Run (billing account plus more Google Cloud setup
for the same result); Vercel for the web app (a second provider for no gain).

### 4a. Which Firebase project (owner's preference, 2026-11-16: reuse an existing one)

What could be established without touching any cloud account:

- The repository has never contained a real project: no `.firebaserc`, no `.env.local`, no
  project id or web config in any commit on any branch. All development here used the
  Emulator Suite (project `demo-aquatrack`, which is not a real project).
- The Firebase CLI on the development Mac is signed in, and the only project it has been
  used with belongs to a different, unrelated application. That project must not be used:
  security rules, the user list and the default bucket are project-wide, so AquaTrack's
  rules would replace that application's rules and its users would share one sign-in pool.
- Whether an AquaTrack project exists in the student's or the owner's Firebase account is
  therefore **unknown** and can only be read in the Firebase console by its owner.

An existing project is safe to reuse only if all of these hold (console checks):

1. It was created for AquaTrack and no other app or workflow uses it (Project settings →
   Your apps; Hosting, Functions, Extensions empty or AquaTrack's own).
2. Its Firestore and Storage rules are AquaTrack's (or the untouched defaults), because
   the restricted rules replace the published rule set of the default database and bucket.
3. Its existing users are either none, or test accounts nobody else relies on. Under the
   restricted rules an account that is not listed can do nothing; anyone who must keep
   access has to be listed in `AQUATRACK_ALLOWED_UIDS`.
4. Existing Firestore and Storage content is AquaTrack's own. The demo adds documents in
   the same collections under the demo accounts' uids and one file under
   `demo_fixtures/pose/`; it deletes or migrates nothing that exists.

What the deployment changes in the project: the two published rule sets; the demo
accounts added by the owner; the custom claim `aquatrack_demo` on listed accounts (other
claims on any account are kept; the claim is removed only from accounts that carry it
and are not listed); one uploaded pose file; a service-account key. Everything else is
left as it is. If any check fails, the demo's data cannot be separated inside that
project without rewriting how the app addresses Firestore and Storage, and the smallest
alternative is a project of its own.

### Blockers found in the actual setup

1. The GitHub repository `jk0103/Aquatrack` is public. **Owner's decision (2026-11-16): the
   source may be public; deploy from this repository, branch `feature/aquatrack-completion`.**
   No new repository. The push itself still waits for the owner's go-ahead after the
   pre-push review (section 11). No licence file is added, so the code is visible but not
   licensed for reuse; that is unchanged and remains the owner's separate decision.
2. Cloud Storage for Firebase requires the **Blaze (billing-enabled) plan**: for any new
   default bucket, and since 2026-02-03 to keep using an existing one (Firebase FAQ on the
   2024 storage changes). This applies to an existing project as much as to a new one.
3. The backend needs a service-account key for the demo project. The owner creates it and
   stores it as a Render Secret File; it is never put on this Mac, in git or in a chat.
4. New projects name their bucket `<project>.firebasestorage.app`; set
   `FIREBASE_STORAGE_BUCKET` (the code's default is `.appspot.com`).
5. Not measured: memory of the API on a 512 MB instance (OpenCV decodes the video to
   identify it). If it is short, the next instance size is the fix.

No Firestore composite index is needed (all queries are single-field).

## 5. Cost (estimates, not guarantees)

- Render: two Starter instances, about US$7 per month each, billed by the second while
  they exist; a few days is roughly US$1–3. A card is required. Free instances sleep after
  15 idle minutes and take up to about a minute to wake, which is a real risk in front of
  a class; if cost must be zero, use Free and open the site a few minutes early. Prices and
  any workspace fee must be read on Render's pricing page at approval time (not verified
  against the live page here).
- Firebase Blaze: Auth, Firestore and Storage at this scale (a handful of accounts, a few
  12 MB uploads) are expected to stay inside the no-cost quotas; expected cost US$0. Blaze
  has no hard spending cap: set a budget alert (for example US$1), which notifies and does
  not stop spending. Put the bucket in `us-central1`, `us-east1` or `us-west1`.
- No GPU, no models, no OpenAI calls (`AQUATRACK_LLM_PROVIDER` unset).
- Recurring cost stops when the Render services are deleted and the Firebase project is
  deleted or billing is unlinked.

## 6. Deployment order (after approval)

1. After the owner's go-ahead: push `feature/aquatrack-completion` to `origin` (no force,
   `main` untouched).
2. Firebase console, in the project chosen in section 4a (note the current rules first, so
   they can be put back): Blaze if not already, add a budget alert → Authentication:
   enable Email/Password, disable sign-up if available → Firestore (production mode) →
   Storage (US region) → paste `firebase/restricted/firestore.rules` and
   `firebase/restricted/storage.rules` into the two Rules editors and publish.
3. Authentication → Add user for each demo account (the owner chooses the passwords);
   copy each **User UID**.
4. Storage: upload
   `data/precomputed_pose/ce32d556…c3.rawpose.npz` to `demo_fixtures/pose/` (same file name).
5. Project settings → add a Web app (copy the config values) → Service accounts →
   generate a key (keep the file private).
6. Render → New → Blueprint → `jk0103/Aquatrack`, branch `feature/aquatrack-completion`. Fill in the values marked
   `sync: false`; add the key as Secret File `firebase-demo.json` on the API service.
   Deploy the API first, then set `API_URL` on the web service to the API's `https://…
   onrender.com` address and deploy it (the address is read at build time).
7. Check `https://<api>/health/ready` → `"access":"restricted","demo":true`.
8. From another browser or device: run section 7.

API environment: `AQUATRACK_ENV=staging`, `AQUATRACK_ALLOW_PRODUCTION_FIREBASE=1`,
`AQUATRACK_DEMO=1`, `AQUATRACK_ACCESS=restricted`, `AQUATRACK_ALLOWED_UIDS`,
`AQUATRACK_POSE_SOURCE=precomputed`, `AQUATRACK_PRECOMPUTED_POSE_DIR`,
`AQUATRACK_WORKER=embedded`, `FIREBASE_PROJECT_ID`, `FIREBASE_STORAGE_BUCKET`,
`GOOGLE_APPLICATION_CREDENTIALS=/etc/secrets/firebase-demo.json`.
Web environment: `API_URL`, `NEXT_PUBLIC_AQUATRACK_ACCESS=restricted`,
`NEXT_PUBLIC_AQUATRACK_DEMO=1`, `NEXT_PUBLIC_FIREBASE_API_KEY`, `…_AUTH_DOMAIN`,
`…_PROJECT_ID`, `…_STORAGE_BUCKET`, `…_APP_ID`. Never set
`NEXT_PUBLIC_FIREBASE_EMULATORS` or any `*_EMULATOR_HOST` on a host: the API refuses to
start its store with emulator hosts in staging, and the emulators stay on this Mac.

## 7. Checks on the deployed site (not yet possible)

- `/signup` shows "Sign-up is closed".
- A demo account signs in; the approved video uploads, analyses, shows results, feedback,
  the saved-pose notice, plays, and a timestamp moves the player.
- A different video fails with the demonstration message.
- An account that exists in Firebase but is not listed is refused at login; with its token,
  `GET <api>/me` is 403.
- Without a login, `GET <api>/me` is 401.

## 8. Afterwards

Delete each video from its page (or the account from Profile; both remove Firestore and
Storage data through the backend). Then delete the two Render services, delete the
service-account key, republish the rules noted in step 2 if the project is kept, and
remove the demo accounts. Delete the project only if it was created for the demo.
