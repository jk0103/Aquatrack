## 2. 모델 선정

### 2.1 검출기: `yolo11m.pt` (확정)

| 설정 | 값 |
|---|---|
| 가중치 | `yolo11m.pt` (COCO 사전학습, 재학습 없음) |
| 입력 크기 | 640 |
| 신뢰도 임계값 | 0.15 |
| 수영자 선택 | 이전 박스와 겹치는 것 우선(추적), 첫 프레임은 면적×신뢰도 |
| 놓친 프레임 | 학생의 `BoxTracker`로 최대 0.5초 박스 유지 |

근거 (SWIM-360 수중 144프레임, 사람이 그린 정답 박스):
- 수영자 찾음 98.6%, IoU≥0.3 98.6%, IoU≥0.5 84.7~85.4%, 엉뚱한 대상 0%.
- 현재 코드가 실제로 쓰는 대체 모델 `yolo26n-pose`는 72.9%, 학생 모델 `swim_pose.pt`@640은 91.7%.
- 이 박스로 RTMW를 돌리면 PCK@0.2가 0.841 (정답 박스 0.870).
- 속도(4K 프레임당): L4 GPU 16ms, M1 Pro MPS 36ms, M1 Pro CPU 136ms.

대안 (설정으로 남김):
- `yolo11x.pt`@640: 수중 100% 검출, 속도 2배. 품질 우선 옵션.
- `swim_pose.pt`@1280: 수상에서 가장 나았음. 단 근거가 12프레임뿐이라 **잠정**.

### 2.2 포즈 추정기: RTMW-x 384×288 stock (MVP 확정, 비교 근거는 제한적)

- 정답과 비교해 측정한 포즈 모델은 RTMW-x뿐임: 수중 PCK@0.2 **0.87**, 부위별로 머리 0.93, 어깨·엉덩이 0.97, 무릎·발목 0.96, **팔꿈치·손목 0.59**.
- ViTPose-B와 ViTPose-L(SwimXYZ)는 학생 노트북에 출력이 저장되어 있지 않아 수치로 비교할 수 없음. 따라서 "평가된 모델 중 가장 좋다"가 아니라 **"정량 검증된 유일한 모델이고, 기존 코드와 기술 지표가 이 모델의 133개 점(손·발 포함)을 전제로 한다"**는 이유로 선정함.
- 속도: Colab CPU에서 프레임당 중앙값 124ms. 가중치 369MB.

### 2.3 지원 범위와 한계

| 촬영 조건 | 상태 |
|---|---|
| 수중 측면, 자유형 | **지원** (검출·포즈 검증됨, 기술 지표 구현됨) |
| 수상 측면 | **제한적/실험적.** 검출이 불안정함. 품질 지표로 걸러서 측정 가능한 것만 보여줌 |
| 위에서 촬영, 정면 | 평가한 적 없음 → 아직 지원하지 않음 |
| 배영·평영·접영 | 검출은 수중에서 됨. 지표 로직이 없음 (평영은 사이클 검출 방식부터 다름) |

불확실성: 벤치마크가 고정 4K 카메라의 6개 시퀀스뿐임. 휴대폰으로 손에 들고 찍은 영상에서는 검증한 적이 없음.

### 2.4 설정 방식

`ModelConfig` 하나에 검출기 가중치·입력 크기·임계값·선택 규칙·포즈 모델·장치를 담고, 환경변수/설정 파일로 바꿀 수 있게 함. 모든 분석 결과에 사용한 설정과 가중치 해시를 기록함.

### 3.2 부족한 것 (Phase 1에서 추가)

1. **원본 출력에 빠진 정보:** 프레임별 박스, 검출 신뢰도, 박스 출처(검출/유지), 검출기·포즈 모델 이름과 해시, 타임스탬프. → `WholeBodySequence`에 필드 추가(기존 파일도 읽히게).
2. **수영자 선택:** 현재 "가장 큰 박스". → 추적 선택으로 교체하고, 박스가 갑자기 멀리 뛰면 **수영자 바뀜**으로 보고 구간을 끊음. 끊긴 지점을 넘는 보간·스무딩은 하지 않음.
3. **품질 리포트(신규):** 유효 포즈 프레임 비율, 관절별·부위별(머리/몸통/팔/다리) 검출률, 보간된 비율, 제거된 비율(사유별), 박스 유지 비율, 가장 긴 누락 구간, 신뢰 가능한 사이클 수, 전체 신뢰 등급(충분/제한적/부족), 측정 불가 사유.
4. **임계값 근거 문서화:** 학생 값을 기준으로 두고, 실제 수중 영상의 RTMW 출력에서 점을 일부러 지운 뒤 보간 오차가 누락 길이에 따라 어떻게 커지는지 재서 0.2초가 적절한지 확인함. 추론은 Colab에서, 분석은 Mac에서 함. 근거와 결과를 문서로 남김.

원칙: 긴 가림 구간은 채우지 않음. 채운 값은 낮은 신뢰도로 표시함. 부족하면 "측정 불가"를 반환함.

## 4. 생체역학 지표 계획

개요서의 9개 분석 대상과 현재 코드의 대응:

| 분석 대상 | 기존 지표 (`technique.py`) | 수중 측면 자유형에서 | 할 일 |
|---|---|---|---|
| 1. 머리 위치 | `head_angle` | 측정 가능 | 실제 영상 검증 |
| 2. 몸 정렬 | `body_line_angle`, `hip_depth_below_shoulders` | 측정 가능 | 실제 영상 검증 |
| 3. 팔 궤적 | 팔꿈치 각도, 캐치 자세, 당기기 깊이, 입수·리치, 궤적 편차 | 카메라 쪽 팔은 가능, 반대쪽 팔은 신뢰도 절반 | RTMW 팔 정확도(0.59)를 반영해 신뢰도 기준 강화 |
| 4. 호흡 타이밍 | `breath_timing`, `breaths_per_arm_cycle` | **실험 단계** | 검증 전까지 "실험적" 표시 |
| 5. 몸통 회전 | 상태값만 있음 | **측정 불가** (위·정면 영상 필요) | 한계를 화면에 설명 |
| 6. 킥 리듬 | 사이클당 킥 수, 킥 크기, 무릎 굽힘, 발끝 | 측정 가능 | 실제 영상 검증 |
| 7. 스트로크 일관성 | **없음** | 계산 가능 | **신규:** 사이클 길이와 주요 지표의 사이클 간 변동 |
| 8. 좌우 균형 | `balance` | 측면에서는 제한적 | 한계 명시 |
| 9. 구간별 변화 | 지표가 구간(start/middle/end)별로 저장됨 | 계산 가능 | **신규:** 구간 간 변화 요약 |
| 추가 | 스트로크 수, 사이클, 페이스, 스트로크당 거리 | 가능 | — |

Phase 2의 일은 새로 쓰는 것이 아니라 다음 네 가지임:
1. **지표 명세서:** 지표마다 필요한 관절, 계산법, 적용 영법, 지원 촬영 각도, 최소 품질 조건, 신뢰도, 측정 불가 조건을 문서와 코드(레지스트리)로 정의.
2. **신규 지표 2종:** 일관성, 구간 변화. 기존 사이클별 값에서 계산함.
3. **실제 영상 검증:** 수중 측면 자유형 영상 몇 개를 Colab에서 추론하고, 키프레임 그림으로 각 지표가 맞는 위치를 재는지 눈으로 확인함. 정답 라벨이 없으므로 "과학적으로 검증됨"이 아니라 "실제 영상에서 타당성 확인"까지임.
4. **결과 계약:** 프론트엔드가 읽는 구조화된 결과 형식 확정 (값, 단위, 신뢰도, 근거 프레임 시각, 측정 불가 사유).

모든 계산은 결정적이고 테스트 가능하며 언어 모델과 무관함.

## 5. 개인화 이슈 검출

**규칙 기반 엔진**으로 구현함. 하나의 이상적 자세와 비교하지 않고, 근거가 강한 순서대로 다음 기준을 씀:

1. **자기 안에서의 변동:** 한 영상 안에서 사이클마다 값이 얼마나 흔들리는가 (일관성).
2. **구간 변화:** 끝 구간이 처음 구간보다 얼마나 달라졌는가.
3. **좌우 차이:** 측정 가능한 범위에서.
4. **자기 과거와의 비교:** 조건이 같은 이전 영상들의 중앙값 대비 좋아졌는지, 나빠졌는지, 반복되는지.
5. **넓은 참고 범위:** 문헌 근거가 확인된 경우에만, 수준별로 넓게 잡아 보조적으로 사용.

규칙마다 정의하는 것: 필요한 지표, 최소 신뢰도와 최소 사이클 수, 임계값과 그 근거, 연결된 근거 자료, 적용 대상(수준·목표).
- 임계값은 그 지표의 측정 잡음(영상 안 사분위 범위)보다 커야 함. 잡음 수준의 차이는 이슈로 보지 않음.

개인화 방식:
- **수준:** 허용 폭과 설명 방식이 달라짐.
- **목표·거리:** 단거리는 스트로크 수·캐치, 장거리는 일관성·구간 변화·몸 정렬에 가중치.
- **본인이 적은 약점:** 측정 근거가 있을 때만 우선순위를 높임. 근거가 없으면 "이번 영상에서는 확인되지 않음"으로 답함.
- **히스토리:** 반복되는 이슈는 우선순위를 높임.

이슈 하나의 출력: 관찰된 패턴, 근거 수치, 빈도(N사이클 중 n회), 영상 시각, 신뢰도, 이전 세션 대비, 기술·효율에 대한 가능한 의미.
근거가 부족하면 이슈를 만들지 않음. "뚜렷한 이슈 없음"도 정상 결과임. 기록 향상에 대한 인과 주장은 하지 않음.

## 6. 개선 우선순위와 피드백 구조

```
이슈 목록 → 점수화(크기 × 신뢰도 × 목표 관련성 × 반복 여부) → 상위 최대 3개
          → 우선순위 카드(구조화 데이터) → ① 템플릿 문장 (항상 동작)
                                        → ② LLM 설명 (있으면 대체, 실패하면 ①)
```

- 기준 점수를 넘는 것이 없으면 3개를 채우지 않음.
- 우선순위 카드: 이슈, 왜 중요할 수 있는지, 근거 수치, 권하는 동작 조정, 수준에 맞는 설명, 다음에 집중할 것, **다음 영상 체크포인트**, 신뢰도와 한계.
- **체크포인트**는 이슈의 지표에서 자동 생성함 ("다음 영상에서 X 지표가 현재 값 A에서 어느 방향으로 변하는지 확인"). 조건이 같은 다음 영상이 올라오면 자동으로 결과를 평가해 보여줌.
- **LLM 계층 (Claude API):**
  - 입력: 구조화된 지표·이슈·수준·목표만. 영상, 이름, 이메일은 보내지 않음.
  - 출력 검증: 정해진 형식, 입력에 없는 숫자·이슈·참고문헌이 있으면 폐기하고 템플릿 사용.
  - 모델은 설정값으로 두고 Phase 4에서 비용과 품질을 재서 정함.
  - 어느 쪽 문장인지(`template`/`llm`) 결과에 기록함.
- 사람 코치가 검토했다는 인상을 주는 표현은 쓰지 않음.

미정: 화면 언어. 현재 UI는 영어임.

## 7. 과학적 근거와 RAG

**권장: 직접 선별한 근거 라이브러리. 벡터 검색 방식의 RAG는 MVP에서 만들지 않음.**

- 형식: 저장소 안의 구조화 파일. 항목마다 주장, 연결된 지표·이슈, 연구 대상(연령·수준), 적용 가능한 수준, 제목·저자·연도·DOI, 한계, 확인한 날짜.
- 이유:
  - 필요한 근거는 지표 수에 비례하는 수십 건 규모임.
  - 조회가 "이 지표의 근거"로 정해져 있어 검색이 필요 없음.
  - 어떤 문장이 어떤 논문에서 왔는지 그대로 추적할 수 있음.
- RAG를 다시 검토할 시점: 근거가 수백 건을 넘거나, 자유 질문 답변 기능을 넣을 때.
- 검증 절차: DOI 페이지를 실제로 열어 서지 정보와 해당 결과를 확인한 것만 등록함. 기억에 의존한 인용은 금지. 확인하지 못한 주장은 "일반적인 지도 관행(연구로 확인되지 않음)"으로 표시하거나 쓰지 않음.
- 엘리트 성인 대상 연구는 초보자·어린 수영자에게 그대로 적용하지 않고, 적용 범위를 항목에 적음.
- 이 제안서에는 특정 논문을 싣지 않음. 문헌 조사는 Phase 4에서 하고, 조사 결과를 검토받음.

## 8. 히스토리와 스트로크 최적화 설계

### 저장 구조 (Firestore + Storage)

| 위치 | 내용 |
|---|---|
| `videos/{id}` (기존) | 세션 정보(날짜, 영법, 거리, 풀 길이, 기록, 촬영 각도, 메모), 상태, 분석 요약 |
| `videos/{id}/analyses/{버전}` (신규) | 지표 요약, 품질 리포트, 이슈, 우선순위, 체크포인트, 피드백, 모델 설정·버전 |
| Storage `analysis/{uid}/{videoId}/` (신규) | 원본 포즈, 정리된 포즈, 사이클별 상세 값, 키프레임 이미지 |

Firestore 문서는 1MB 제한이 있어 큰 배열은 Storage에 둠. 분석 문서는 백엔드만 쓰고, 본인만 읽음.

### 비교 규칙

- **비교 가능 조건:** 같은 영법 + 같은 촬영 각도. 풀 길이·거리가 다르면 해당 지표에 주의 표시. 조건이 다르면 비교하지 않고 이유를 보여줌.
- **변화 판정:** 세션별 중앙값과 사분위 범위로 추세를 그림. 측정 잡음을 넘는 변화만 "개선/악화"로 표시.
- **반복 이슈:** 최근 비교 가능한 3개 세션 중 2개 이상에서 같은 이슈.
- **기록과의 관계:** 기록 변화와 지표 변화가 같은 시기에 나타났는지만 서술함 ("함께 나타남"). 세션이 3~4개 미만이면 표시하지 않음. 인과 표현은 쓰지 않음.
- **최적화 요약:** 특징적인 움직임 패턴, 반복 이슈, 개선된 요소, 기록 향상과 함께 나타난 변화, 현재 우선순위, 다음 체크포인트. 결정적 집계로 만들고, LLM은 선택적으로 문장만 다듬음.

## 9. 훈련 추천과 캘린더 (보조 기능)

- **드릴 라이브러리:** 드릴마다 대상 이슈, 수준, 안전 표시, 근거(확인된 연구 또는 "일반적인 지도 관행") 연결.
- **계획 생성(규칙 기반):** 상위 우선순위 + 가능한 요일 + 세션 길이 → 주간 기술 연습 계획. 본인 훈련 안에 넣는 10~20분 기술 블록이며, 전체 운동량을 짜는 프로그램이 아님.
- 각 항목에 "어떤 이슈를 위한 것이고 왜 도움이 될 수 있는지"를 표시.
- 분석 데이터가 부족하면 "일반 제안"으로 명확히 표시.
- 금지: 숨 참기 훈련, 과도한 양, 기록 보장 표현.
- 캘린더: 본인이 직접 관리(완료 표시, 이동). 새 분석이 나오면 다음 주 계획을 조정.
- 프로필에 이미 주당 횟수·세션 길이가 있음. 추가로 필요한 것은 가능한 요일 정도.
- 기존 Training·Calendar 화면은 유지하고 예시 데이터를 실제 데이터로 바꿈.

## 10. 프론트엔드·백엔드·데이터베이스 변경

### 백엔드 (FastAPI)

| 모듈 | 내용 |
|---|---|
| 영상 수집 | Storage에서 임시 폴더로 받기, 형식·길이 검사 |
| 추론 | `ModelConfig`, 추론 백엔드 인터페이스: `local`(서버·GPU), **`precomputed`**(Colab에서 만든 원본 포즈 파일을 읽음) |
| 시간 처리 | 기존 `cleanup` + 품질 리포트 |
| 지표 | 기존 `cycles`, `technique` + 일관성·구간 변화 |
| 해석 | 이슈 규칙 엔진, 우선순위 |
| 설명 | 템플릿 + LLM |
| 훈련 | 드릴 라이브러리, 계획 생성 |
| 저장 | Firestore·Storage 기록 (Admin SDK) |

- API: 분석 시작(`POST /videos/{id}/analyze`, 로그인·소유자 확인), 재시도. 상태는 Firestore 문서(`uploaded → analyzing → ready/failed`, 오류 사유, 시도 횟수)로 전달하고 프론트는 실시간 구독.
- 분석은 백그라운드 작업으로 실행. MVP는 서버 안의 단일 작업 큐, 이후 필요하면 별도 워커로 분리.
- 현재 로그인 없이 열려 있고 쓰이지 않는 `POST /videos`는 제거하거나 인증을 붙임.
- 모듈 사이는 버전이 붙은 구조화 계약(pydantic)으로 주고받음.
- `precomputed` 백엔드 덕분에 Mac에는 가중치 없이도 전체 흐름을 개발·테스트할 수 있음.

### 프론트엔드 (Next.js, 기존 디자인 재사용)

- 온보딩·프로필: 주 종목, 목표 기록, 목표, 본인이 생각하는 약점, 가능한 요일 추가.
- 업로드: 분석 시작 연결, 촬영 조건 안내(수중 측면 권장).
- 분석 상태, 결과 화면: 지표(측정 불가 사유 포함), 품질 배지, 우선순위, 체크포인트, 근거 프레임으로 이동.
- 히스토리·진척: 실제 데이터, 비교 불가 사유 표시.
- Training·Calendar: 실제 데이터.
- `mock.ts` 의존 화면 9곳을 단계적으로 실제 데이터로 교체. 그 전까지 예시는 예시로 표시.

### 데이터베이스·규칙

- `profiles`: 새 필드 허용 (현재 규칙은 정해진 키만 허용).
- `videos/{id}/analyses`: 본인 읽기 전용, 쓰기는 백엔드만.
- 계획·캘린더 컬렉션: 본인만 읽고 씀, 값 검증.
- Storage 분석 산출물: 본인 읽기, 백엔드 쓰기.
- 영상 삭제: 현재 규칙이 막고 있음. 본인 삭제 기능이 필요함 (개인정보 관점).

## 11. 구현 단계

| 단계 | 내용 |
|---|---|
| **0. 저장소 준비** | 병합으로 통합(§14), 검증, `uv` 설치, 에뮬레이터로 기존 흐름 점검, 사양·결정 문서화 |
| **1. 모델 확정과 포즈 품질** | `ModelConfig`, 추적 선택, 원본 출력 확장, 수영자 바뀜 처리, 품질 리포트, 임계값 근거 문서, `precomputed` 추론 백엔드, 결과 계약 초안 |
| **2. 생체역학 지표** | 지표 명세서, 일관성·구간 변화, 실제 영상 검증, 결과 계약 확정 |
| **3. 개인화 이슈 검출** | 프로필 필드 추가, 규칙 엔진, 반복 패턴, 신뢰도, 우선순위 |
| **4. 피드백과 근거** | 템플릿 문장, 체크포인트, 근거 라이브러리(검증된 문헌), LLM 계층과 검증기, API 없을 때 동작 |
| **5. 히스토리와 최적화** | 저장 구조, 히스토리·진척 실제 데이터, 비교 규칙, 추세, 최적화 요약, 체크포인트 추적 |
| **6. 훈련과 캘린더** | 드릴 라이브러리, 계획 생성, 화면 연결, 새 분석 반영 |
| **7. 통합과 출시 준비** | 업로드→분석 작업 완전 연결, 오류·재시도, 전체 흐름 테스트, 인증·소유권 테스트, Render·GPU 필요성 평가 |

**순서에 대한 제안:** 요구사항 문서는 업로드→분석 연결을 Phase 7에 둠. 통합 위험을 줄이려면 **분석 작업의 뼈대(상태 문서, 결과 저장, 계약)를 Phase 1~2에서 `precomputed` 백엔드로 먼저 세우고**, Phase 7에서는 실제 추론 서버 연결과 마무리만 하는 편이 안전함. 이 방식으로 진행할지 결정이 필요함.

## 13. 단계별 완료 기준

| 0 | 작업 브랜치에 세 갈래 + 연구 브랜치가 병합됨(학생 이력 보존, `main` 그대로, 강제 푸시 없음). 백엔드 테스트·ruff·프론트 lint·build 통과. 에뮬레이터에서 가입→프로필→업로드→히스토리가 실제로 동작. 예시 표시 복원. 결정 사항 문서화 |
| 1 | 설정만 바꿔 검출기 교체 가능. 원본 포즈 파일에 박스·출처·모델 정보 포함. 수영자 바뀜에서 보간이 끊기는 테스트 통과. 품질 리포트가 실제 수중·수상 영상 각각에서 타당한 값(수상은 "제한적/부족")을 냄. 임계값 근거 문서 존재. 가중치 없이 `precomputed`로 전체 파이프라인 테스트 통과 |
| 2 | 지표 명세서 완성. 일관성·구간 변화 구현과 합성 테스트. 실제 수중 측면 자유형 영상 3개 이상에서 키프레임 검토 기록. 측정 불가 조건에서 사유가 반환됨. 결과 계약 확정 |
| 3 | 프로필 새 필드 저장(규칙 테스트 포함). 근거 부족 시 이슈가 생성되지 않는 테스트. 수준·목표가 다르면 우선순위가 달라지는 테스트. 이슈마다 수치·빈도·시각·신뢰도 포함 |
| 4 | 우선순위 최대 3개와 체크포인트 생성. API 키 없이도 완전한 피드백 표시. LLM 출력에 입력에 없는 숫자·참고문헌이 있으면 폐기되는 테스트. 근거 라이브러리의 모든 항목에 확인 기록 |
| 5 | 분석 결과가 저장되고 다시 불러와짐. 다른 사용자의 데이터 접근이 거부되는 규칙 테스트. 조건이 다른 세션은 비교되지 않고 사유가 표시됨. 세션 2개 이상에서 추세와 반복 이슈 표시. 예시 데이터가 실제 수치로 표시되는 화면 없음 |
| 6 | 계획의 모든 항목이 이슈와 연결됨. 분석이 없으면 "일반 제안" 표시. 금지 항목이 생성되지 않는 테스트. 캘린더에서 본인이 수정·완료 가능 |
| 7 | 실제 영상 업로드부터 저장된 분석 히스토리까지 한 번에 동작. 요구사항 14절의 12개 시나리오 결과표(구현/테스트/실데이터 검증/미완/차단/미검증 구분). 추론 시간·메모리·비용 실측 보고. 배포는 하지 않음 |

## 14. 권장 시작 작업 (Phase 0)

1. **비파괴 통합 (병합만 사용, rebase·강제 푸시 없음):**
   - 작업 브랜치는 현재 `main`과 같은 커밋이고, 이 커밋은 모든 학생 브랜치의 조상임. 따라서 `web-ui-improvements`로 빨리 감기(fast-forward)하면 학생 이력이 그대로 들어옴.
   - `rtmw-pose` 병합 (충돌 없음 확인됨).
   - `ui-design` 병합: 7개 파일 충돌을 직접 해결. 실제 데이터 로직은 `web-ui-improvements` 쪽, 디자인은 `ui-design` 쪽을 살리고 예시 표시는 복원.
   - 연구 브랜치 2개 병합 (README만 충돌).
   - 병합은 로컬 병합 커밋을 만듦. Phase 0 승인에 이 로컬 커밋을 포함할지 확인이 필요함. 푸시는 별도 승인.
2. 검증: 백엔드 테스트, ruff, 프론트 lint·build.
3. `uv` 설치 (Homebrew).
4. Firebase 에뮬레이터로 기존 흐름(가입, 프로필, 업로드, 히스토리) 실제 동작 확인.
5. 문서: `CLAUDE.md`(사양), 모델 선정 문서, 이 제안서. `experiments/detector_comparison`의 스크립트와 보고서(데이터 제외)를 저장소에 넣을지 결정.
6. 정리: 오래된 PR #1·#2 처리 방침, 학생 미공개 작업 push 요청, Drive 공유 설정 복구.
